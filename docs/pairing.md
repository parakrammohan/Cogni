# Pairing

A caregiver and a patient become *paired* to share one patient's care
data and live state. Pairing is two-way: either side may generate a
short invite code, the other side keys it in.

## Cardinality

- A patient is paired with **at most one** caregiver. Enforced by a
  `UNIQUE` constraint on `pairings.patient_id`.
- A caregiver may have **N** paired patients (multi-patient UI lands
  post-MVP; current selection picks the first paired patient).
- Either side can break the pairing.

## Lifecycle

```
┌──────────────┐   POST /pairing/invite   ┌────────────┐
│  Inviter     │ ───────────────────────▶ │  Backend   │
│ (any role)   │                          │            │
└──────────────┘ ◀──────────────────────  └────────────┘
                  { code, expires_at }

share the code out-of-band (read it aloud, text, in person)
                          │
                          ▼
┌──────────────┐  POST /pairing/redeem    ┌────────────┐
│  Redeemer    │ ───────────────────────▶ │  Backend   │
│ (other role) │     { code }             │ Pairing    │
└──────────────┘                          │ row created│
                                          └────────────┘
```

### Two roles, one symmetric flow

Either a caregiver or a patient can be the *inviter*. The redeemer must
be of the opposite role; the backend enforces it in
`crud_pair.redeem()` and returns a clear error if both sides have the
same role. The resulting `Pairing` row always stores the caregiver on
`caregiver_id` and the patient on `patient_id`, regardless of who
generated the code.

## Endpoints

| Method | Path | Auth | Purpose |
|---|---|---|---|
| `GET` | `/api/v1/pairing/status` | session | Role-aware projection of the current pairing(s) |
| `POST` | `/api/v1/pairing/invite` | session | Generate a code (15-min TTL) |
| `POST` | `/api/v1/pairing/redeem` | session | Consume a code, form the pairing |
| `DELETE` | `/api/v1/pairing[?patient_id=…]` | session | Break the pairing |

`DELETE` with no body breaks the caller's own pairing (patient side).
A caregiver must pass `?patient_id=…` since they may have several.

`/auth/signup` also accepts an `invite_code` so new users can sign up and pair in one step. If the code is invalid the signup still succeeds; the user can redeem later.

## Code format

- 6 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` — no I, O, 0, 1 (confusion-resistant).
- Code space: 32^6 ≈ 1.07 billion.
- Stored uppercase. Comparisons are case-insensitive on input.

## Security

Defence-in-depth so an attacker who has *no* relationship with the
inviter can't slip into the pair:

| Control | Effect |
|---|---|
| 15-min TTL (`INVITE_TTL` in `crud_pair`) | Brute-force window is tiny. |
| Single active code per inviter | Generating a new code invalidates the old one. So at most one code is live at any time per inviter. |
| Per-user rate limit on redeem (8 / minute) | Caps online guessing speed. |
| Per-IP rate limit on redeem (15 / minute) | Defends against a single attacker using multiple accounts. |
| Same-role + self-redeem rejected | Backend `ValidationError` — code generated by a caregiver can't be redeemed by another caregiver, and you can't redeem your own code. |
| Patient-uniqueness | `pairings.patient_id` is unique — a stolen code from a paired patient is useless. |
| TLS-everywhere | Code only exists in HTTPS responses + cookies. |

Effective math: at the rate-limit ceiling an attacker gets ≤ 225
attempts per 15-min code window. Against ≤ 1 live code in a 10^9
space, the per-window guess probability is ~ 1 in 4.4 million.

### What's still out of scope

- No SMS / email delivery of the code — it's shown to the inviter on
  screen and they share it out-of-band. The chat/voice channel they use
  is the trust boundary.
- No 2FA or phone-number verification.
- No persistent revocation list — when a pairing is broken, future
  patient state isn't shared, but logs/old data the caregiver has
  already pulled aren't retroactively wiped.

## Frontend (PairingCard)

`src/components/PairingCard.tsx` is the shared UI rendered on **both**
roles' Profile scenes. Same component, role-aware copy.

States:
- **Loading**: spinner + "Checking pairing status…" before the first
  `/pairing/status` resolves. We deliberately don't render the empty
  "not paired" copy until status confirms — a flash of false negative
  is bad UX.
- **Unpaired**: side-by-side "Share your code" + "Enter their code"
  cards. Both sides work for both roles.
- **Paired**: row(s) listing the partner, with an Unpair button per
  pairing.

Generated codes show a live countdown (recomputed every second from
`expires_at`). "Regenerate" cancels the prior code server-side.

Patient signup flow accepts an `invite_code` field directly in the
signup form so a new patient can hand their caregiver a code and have
them sign up + pair in one step.

## Demo accounts

The backend seeds `demo-caregiver` ↔ `demo-patient` paired on every
boot (`backend/app/seed.py`). The pairing only inserts if one doesn't
already exist for the patient — i.e. idempotent.
